# GetCard: следы карточных провайдеров и карта API

Дата анализа: 14 сентября 2026 года. Источник: локально сохранённые страницы `getcard.one` и их JavaScript. Анализ статический: без входа в аккаунт, обращения к рабочему API, создания платежей или запуска скачанного кода.

## 1. Главный вывод

**В коде GetCard есть прямые признаки интеграции с CardsPro и следы Pay2 в модели карт и транзакций.** Это наиболее содержательные находки по вопросу «через кого выпускают карты».

| Находка | Что установлено | Чего она не доказывает |
| --- | --- | --- |
| `/api/cardspro/kyc` и `/api/cardspro/kyc/start` | Есть клиентский код отдельного KYC-процесса с именем CardsPro, подключённый к мастеру выпуска карты | Юридическое название банка-эмитента; поставщика конкретной уже купленной карты |
| `cardsproProductCode`, `cardsproKycSort` | Схема карточного продукта предусматривает код продукта и настройку KYC CardsPro | Какие значения установлены на рабочем сервере и какие продукты сейчас доступны |
| `pay2_card_last4`, `pay2_tx_id` | Название Pay2 встроено в модель карточных данных и сверку операций | Что все карты сейчас обслуживает Pay2: названия полей могли сохраниться после миграции |
| Обработка merchant, начинающихся на `pay2` и `cardspro` | Оба имени специально распознаются в обработке истории операций | Что CardsPro и Pay2 — одна компания или находятся в определённой договорной цепочке |
| Конфигурации GetCard и VIAPAY в одном модуле | Одна сборка содержит настройки двух брендов; выбран GetCard | Что VIAPAY является эмитентом, а не другим брендом того же приложения |
| `verification.heleket` в конфигурации VIAPAY | Есть след имени Heleket в настройках другого бренда | Что текущий криптоэквайринг GetCard действительно работает через Heleket |

**Рабочая гипотеза:** GetCard — собственная витрина и личный кабинет поверх внешней карточной инфраструктуры. CardsPro — сильный кандидат на роль интеграционного карточного провайдера, особенно для продуктов с внешним KYC; Pay2 — существенный след текущего или прежнего интеграционного слоя. Установить точную связь между ними по сохранённому фронтенду нельзя.

**Прямых упоминаний Luma/Lumo, Ravana или Aifory в карточной интеграции этих файлов не обнаружено.** Отсутствие имени во фронтенде не исключает поставщика на серверной стороне. Данные из ранее обсуждавшегося `A Pro/app.js` к GetCard не переносились.

### 3.5. Что можно и нельзя сказать о банке-эмитенте

Маркетинговые тексты говорят о «зарубежном банке-эмитенте» и «лицензированном партнёре», но не называют банк: `A/139gc3tagtqd3.js`, участки `91700–92500`, `106162–106550`; `A/3hjgukd66676b.js`, участок `25933–26350`.

В конфигурации бренда есть:

```text
issuer.network = "Mastercard"
issuer.productCategory = "MASTERCARD B2B PRODUCT 1"
```

Источник: `A/0f55x1s4ttlms.js`, участок `22960–23300`.

**Mastercard/Visa — платёжные системы, не название банка.** Категория `MASTERCARD B2B PRODUCT 1` тоже не идентифицирует банк.

На рисунке оборота карты строка собирается как `brand.name + " Issuer Ltd."` (`A/16jszpudo-1wk.js`, участок `25499–26000`; также `A/1xogblf7691tk.js`). Это шаблон интерфейса, **не доказательство существования банка «GetCard Issuer Ltd.»**.

Страны в справочнике адресов, упоминание Сингапура в рекламе VPN и география merchant также не доказывают страну выпуска.

## 5. Что действительно видно о пополнении через СБП

Подтверждённая клиентская последовательность:

```text
Пользователь выбирает карту или внутренний счёт
  -> GET /api/wallet/top-up/methods
     сервер возвращает доступные способы, курс, комиссии и лимиты
  -> POST /api/wallet/top-up/rub
     method = "sbp" или "ru-card"
  -> сервер возвращает { url: ... }
  -> браузер переходит на платёжную страницу
  -> внутренний счёт / карта отображаются через API GetCard
```

Источники: `A/30a3c2-6cqb99.js`, участки `15200–18000`, `44700–48400`.

Криптовалютный сценарий отдельно вызывает `POST /api/wallet/top-up`, также получает `url` и переводит пользователя на внешнюю страницу (`40400–44492`). Название `topup_usdt` встречается в аналитике, а текст интерфейса перечисляет USDT, BTC, ETH и другие монеты.

Код также различает **внутренний счёт** и **баланс карты**. Если на счёте достаточно денег, вызывается `POST /api/cards/{id}/top-up`, без новой внешней оплаты. Есть комбинированная оплата: часть со счёта через `walletPartUsd`, остальное через платёжный счёт.

**Не установлено:** кто принимает рубли по СБП, какое юрлицо является получателем конкретного платежа, какой используется эквайер, как происходит дальнейшая конвертация и чем пополняется резерв карточного провайдера. URL платёжной страницы приходит с сервера и в скачанных JS не раскрыт.

Следовательно, схема «рубли на своё РФ-юрлицо → покупка USDT → пополнение провайдера» для GetCard **этими файлами не доказана**. Альтернативы — расчёт через платёжного агента, агрегатора, предварительно пополненный резерв и другие договорные модели.

Финансовые поля `rateRubPerUsd`, `rubFeePercent`, `cryptoFeePercent`, `rubLimits`, а также отдельные курсы для wallet-продуктов приходят с сервера. В коде есть резервное значение криптокомиссии `9` и `CARD_FX_SPREAD_PERCENT=1.5`; это не основание считать их текущими тарифами или чистой прибылью. Комиссия провайдера, себестоимость конвертации и договоры в выгрузке отсутствуют.

## 6. API: общие правила чтения каталога

Ниже **68 уникальных сочетаний HTTP-метода и пути**, непосредственно используемых прикладным кодом. Query-варианты одного маршрута объединены. Отдельно отмечен один путь, найденный только в диагностическом сообщении.

Все `/api/...` в вызовах относительные. Для исходного сайта это `https://getcard.one/api/...`; реальный upstream за сервером неизвестен. Доступность маршрутов, права пользователя и поведение сервера не проверялись.

Обёртки определены, например, в `A/2bf2piaze_6v0.js`, участок `30300–31207`:

| Обёртка | Поведение |
| --- | --- |
| `apiGet(path, options)` | `fetch`, метод GET, `credentials:"include"`, разбор JSON |
| `apiSend(method, path, body, options)` | Указанный метод, JSON, `credentials:"include"` |
| `apiUpload(path, FormData)` | POST, multipart/FormData, `credentials:"include"` |

Для некоторых служебных маршрутов используется прямой `fetch`. Наличие клиентского хука админки **не означает** отсутствие авторизации на сервере.

Параметры и ответы ниже — только видимая часть клиентского контракта, не полная OpenAPI-спецификация. Фактические PAN, CVV, коды подтверждения, пользовательские документы и токены в отчёт не включены.

## 9. Границы выводов и способы уточнения

По этой выгрузке **нельзя достоверно назвать** банк-эмитент, договорного поставщика каждой карты, текущую комиссию процессинга, получателя СБП, закупочный тариф или способ фондирования резерва.

Наиболее полезные дополнительные сведения из собственного аккаунта:

| Источник | Что прояснит |
| --- | --- |
| Уже полученный браузером ответ `/api/card-products` | Реальные BIN, ключи продуктов, признаки внешнего KYC и доступность |
| Ответ `/api/cards/{id}` без секретных реквизитов | Связь купленной карты с конкретным `product_key`, возможные служебные признаки |
| Только домен `urlForUser` из штатного KYC-процесса | Какой внешний сервис проводит верификацию; полную токенизированную ссылку публиковать не нужно |
| Домен платёжной страницы и чек/сведения о получателе собственного платежа | Эквайер/платёжный посредник и фактический получатель рублей |
| Условия обслуживания конкретного карточного продукта | Юридический эмитент и роли посредников |

Для уточнения BIN достаточно первых 6–8 цифр; полный номер, CVV, пароль, cookies и коды подтверждения не нужны. BIN-справочник даёт ориентир по эмитенту, но не всегда устанавливает коммерческого реселлера и может быть неактуален.
