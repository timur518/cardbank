# Оформление заказа и выпуск карты — сквозной алгоритм

Документ описывает полный путь от выбора карты клиентом до активной карты с реальным
балансом, с точным маппингом на существующие модели/поля/сервисы (`app/Services/Integrations/CardsPro`,
`CardProviderOperation`, `CardProviderOperationResolver`, `Income`, `Expense`). Нужен как
спецификация для будущего API-метода оформления заказа.

**Итог по главному вопросу («будет ли P&L точным при таком раскладе»): нет, не сразу.**
Два места в исходном алгоритме дают неверные цифры в уже построенных дашбордах
(`ProfitStatsWidget`, `IncomeExpenseProfitChartWidget`), если оставить как есть — разбор
и починка в шагах 2 и 6, сводка — в разделе «Критичные предложения» в конце.

Также один пункт алгоритма противоречит уже реализованному коду и обработчику вебхуков
CardsPro — это не ошибка в твоей логике, а несостыковка с тем, что было построено раньше
в этом же проекте. Разбор — в шаге 4.

## Действующие модели (для справки)

| Модель | Ключевые поля, которые участвуют в этом алгоритме |
|---|---|
| `CardProduct` | `price_rub`, `provider_issue_cost_usd`, `currency`, `topup_min_amount`/`topup_max_amount` (в валюте продукта), `provider_id`, `provider_product_code`, `billing_*` |
| `Card` | `user_id`, `card_product_id`, `provider_id`, `provider_card_id`, `card_number`, `expiry`, `currency`, `balance`, `price_rub`, `issue_cost_usd`, `status` (enum `CardStatus`), `billing_*`, `issued_at` |
| `Income` | `type` (enum `IncomeType`), `amount`, `currency`, `amount_usd`, `card_id`, `user_id`, `payment_method_id`, `payment_transaction_id`, `payment_status` (enum `IncomePaymentStatus`), `comment` |
| `Expense` | `date`, `category` (enum `ExpenseCategory`), `amount`, `amount_usd`, `card_id`, `provider_id`, `comment` |
| `CardProviderOperation` | `provider_id`, `card_id` (nullable), `type` (enum `CardProviderOperationType`: issue/topup/withdraw/block), `request_id`, `docid`, `status`, `payload` (json), `result`, `error`, `resolved_at` |
| `Setting` | `currency_rate_usd`, `currency_markup_usd_percent` — курс ЦБ и наша наценка (страница «Валютная система») |

Уже реализовано и переиспользуется без изменений: `CardsProService::issueCard()`,
`CardsProWebhookHandler::handleIssue()`, `CardProviderOperationResolver::applyIssue()`,
команда `providers:sync-pending-operations` (страховка на случай потерянного вебхука).

## Шаг 1. Клиент собирает заказ (фронт/ЛК, без записи в БД)

1. Выбирает карту → `CardProduct` → показываем `price_rub` («Цена выпуска, ₽»).
2. Выбирает сумму пополнения — переключатель ₽/$:
   - Берём `Setting::getMany(['currency_rate_usd', 'currency_markup_usd_percent'])`.
   - Наш курс продажи: `rate_sell = currency_rate_usd * (1 + currency_markup_usd_percent / 100)`.
   - Если клиент ввёл сумму в $ (`topup_usd`) → показываем `topup_rub = round(topup_usd * rate_sell, 2)`.
   - Если ввёл в ₽ (`topup_rub`) → показываем `topup_usd = round(topup_rub / rate_sell, 2)`.
   - Валидация границ — `CardProduct.topup_min_amount`/`topup_max_amount` (они в валюте продукта,
     обычно USD — сверяем именно `topup_usd`, а не `topup_rub`).
3. Итог к оплате: `total_rub = price_rub + topup_rub`. Показываем клиенту одной суммой — с этого
   момента `topup_usd` (сколько именно долларов ляжет на карту) — уже зафиксированное число,
   дальше используется как есть, без пересчёта.

Ничего из этого пока не пишется в БД — это калькулятор на фронте/в API-методе расчёта цены.

## Шаг 2. Оформление заказа = создание Income (backend, один API-запрос)

Клиент нажимает «Оплатить». Дальше один запрос делает всё:

1. Создаём **два** отдельных `Income`, а не один общий — см. «Критичное #1» почему.

   **Income №1 — выпуск карты**
   ```
   type              = IncomeType::CardIssue
   amount            = CardProduct.price_rub                         // как есть, уже в ₽
   currency          = 'RUB'
   amount_usd        = round(price_rub / currency_rate_usd, 2)       // курс ЦБ, БЕЗ наценки — см. «Курсы» ниже
   user_id           = $userId
   card_id           = null                                          // карты ещё не существует, см. шаг 4
   payment_method_id = $paymentMethodId
   payment_status    = IncomePaymentStatus::Pending
   comment           = 'Выпуск карты: ' . CardProduct.name
   ```

   **Income №2 — пополнение**
   ```
   type              = IncomeType::CardTopup
   amount            = topup_rub
   currency          = 'RUB'
   amount_usd        = round(topup_rub / currency_rate_usd, 2)       // курс ЦБ, БЕЗ наценки
   user_id           = $userId
   card_id           = null
   payment_method_id = $paymentMethodId
   payment_status    = IncomePaymentStatus::Pending
   comment           = 'Пополнение баланса при выпуске карты'
   ```

   Обе записи держим в памяти вместе с `topup_usd` (точная сумма для `issueCard()`, шаг 4) —
   она не совпадает с `amount_usd` выше, это разные числа (см. «Курсы»).

2. Идёт запрос в платёжную систему (создать платёж на `total_rub = price_rub + topup_rub`).
   В ответ получаем `payment_transaction_id` и ссылку на оплату.

3. Записываем `payment_transaction_id` в обе `Income` (`UPDATE ... WHERE id IN (...)`) — этим же
   значением они позже находятся вебхуком платёжной системы и связываются друг с другом.

4. Отдаём клиенту ссылку на оплату (редирект на платёжную систему).

**Про `card_id = null`:** карты в этот момент физически ещё нет — она появится только после
подтверждения от CardsPro (шаг 5). Это не пропуск, а обязательное следствие того, как уже
устроен `CardProviderOperationResolver` — см. шаг 4.

---

## Шаг 3. Вебхук платёжной системы подтверждает оплату

1. Находим обе `Income` по `payment_transaction_id`, ставим `payment_status = Paid` (обеим сразу
   одним запросом, раз они обе привязаны к одному и тому же платежу).
2. Если оплата **не прошла** (отказ/просрочка) — `payment_status = Failed`, дальше по цепочке
   ничего не запускаем. Карта никогда не создавалась, чистить нечего.
3. Если оплата прошла — передаём в интеграционный модуль: `card_product_id`, `user_id`,
   `topup_usd`, `payment_transaction_id` двух только что оплаченных `Income`.

*(В текущем коде провайдера платежей ещё нет — этот вебхук ещё предстоит реализовать. Пункт
описан на уровне контракта: «по каким полям искать Income» и «что делать дальше», без деталей
конкретного шлюза.)*

## Шаг 4. Инициируем выпуск у CardsPro — здесь правка относительно исходного плана

Исходный шаг 0 предполагал создать `Card` со статусом «В процессе выпуска» ещё до вызова
CardsPro. **Так делать нельзя** — это конфликтует с тем, что уже реализовано:

- `CardProviderOperationResolver::applyIssue()` **сам создаёт** `Card` — причём только в
  момент, когда от CardsPro пришёл `san` (реальный идентификатор карты). До этого момента
  `Card` физически не может существовать: `san` — единственная связь с настоящей картой,
  и до ответа CardsPro его просто неоткуда взять.
- Комментарий в миграции `card_provider_operations` и в `docs/integrations/cardspro.md`
  прямо это фиксирует: «для issue карты ещё нет — заполняется по факту».
- Вебхук `CARD_ISSUE` (`CardsProWebhookHandler::handleIssue()`) уже готов и ждёт ровно такой
  порядок: сначала `CardProviderOperation`, потом (асинхронно) `Card`.

Правильный шаг 4:

1. `CardsProService::for($provider)->issueCard(['productCode' => CardProduct.provider_product_code, 'amount' => $topup_usd, 'currency' => CardProduct.currency])`.
   Это **один** вызов на выпуск и на начальное пополнение сразу — у CardsPro `amount` в
   `issueCard()` это и есть желаемый стартовый баланс, отдельный `topUpCard()` сразу после
   выпуска не нужен.
2. Реакция на ответ:
   - `DECLINED` сразу в ответе — см. «Критичное #4» (клиент уже заплатил, а карта не выпущена).
   - `INPROCESS` или `EXECUTED` — создаём `CardProviderOperation`:
     ```
     provider_id = CardProduct.provider_id
     card_id     = null
     type        = CardProviderOperationType::Issue
     request_id  = <из ответа issueCard()>
     docid       = <из ответа issueCard()>
     status      = CardProviderOperationStatus::Pending
     payload     = ['user_id' => $userId, 'card_product_id' => $cardProductId, 'payment_transaction_id' => $paymentTransactionId]
     ```
   Дальше ничего делать не нужно — итог узнаём либо по вебхуку `CARD_ISSUE`, либо подстрахуется
   `providers:sync-pending-operations`, если вебхук потеряется. Оба пути уже сведены в один
   `CardProviderOperationResolver::resolve()`.

## Шаг 5. CardsPro подтверждает выпуск — карта и расход создаются здесь

Это `CardProviderOperationResolver::applyIssue()`. Сегодня метод создаёт `Card`, но **не делает
ещё двух вещей**, которые нужны именно для этого сценария (нужно дописать):

```php
protected function applyIssue(CardProviderOperation $operation, array $raw): void
{
    // ...существующий код создания Card остаётся как есть, плюс:

    $card = Card::create([
        // ...как сейчас, плюс billing_* — сегодня их нет в create(), а по алгоритму
        // они обязаны сняпшотиться с продукта:
        'billing_country'  => $product?->billing_country,
        'billing_city'     => $product?->billing_city,
        'billing_region'   => $product?->billing_region,
        'billing_address'  => $product?->billing_address,
        'billing_post_code'=> $product?->billing_post_code,
    ]);

    $operation->update(['card_id' => $card->id]);

    // Новое: привязать Income к только что созданной карте.
    Income::where('payment_transaction_id', $operation->payload['payment_transaction_id'] ?? null)
        ->update(['card_id' => $card->id]);

    // Новое: списать себестоимость выпуска в «Расходы» — см. «Критичное #2».
    Expense::create([
        'date'        => now(),
        'category'    => ExpenseCategory::CardIssue,
        'amount'      => round($product->provider_issue_cost_usd * $rate, 2), // rate = currency_rate_usd на момент выпуска
        'amount_usd'  => $product->provider_issue_cost_usd,
        'card_id'     => $card->id,
        'provider_id' => $operation->provider_id,
        'comment'     => "Себестоимость выпуска карты у провайдера (авто, операция #{$operation->id})",
    ]);
}
```

После этого: `Card.status` — то, что вернул `fetchCardSnapshot()` (обычно сразу `Active`,
отдельного промежуточного статуса «оплачено, выпускается у провайдера» между шагом 4 и этим
шагом в модели `Card` нет — см. «Необязательное предложение» в конце, если хочется отличать
эти состояния в ЛК).

## Курсы: где какой брать (важно для точности P&L)

Два разных курса используются в двух разных местах и их нельзя путать:

| Что считаем | Какой курс | Почему |
|---|---|---|
| Сколько ₽ берём с клиента за пополнение (`topup_rub`, шаг 1) | `rate_sell = currency_rate_usd * (1 + currency_markup_usd_percent/100)` | Это цена продажи — клиент платит по курсу с нашей наценкой |
| `Income.amount_usd` (и выпуск, и пополнение) | голый `currency_rate_usd` (без наценки) | Нужен как «справедливая» долларовая оценка рублёвого платежа. Если взять курс с наценкой — наценка (по сути, наша единственная прибыль на пополнениях) исчезнет из отчётов: `amount_usd` совпадёт с `topup_usd`, а `Expense` на пополнение (если появится, см. «Критичное #3») тоже будет ≈ `topup_usd` — прибыль в долларах станет видна как 0, хотя по факту она есть, просто в рублёвой наценке |
| `amount`, отправляемый в `issueCard()` | не курс вообще, а сама сумма `topup_usd`, зафиксированная на шаге 1 | Это операционный параметр («сколько долларов положить на карту»), а не бухгалтерская оценка — их нельзя путать, это разные числа с разным назначением |

Оговорка на будущее: как только появится реальная платёжная система с расчётами в долларах
(см. докблок `ProfitStatsWidget::grossProfitStat()` — там уже заложено, что `amount_usd`
в идеале должен приходить от неё, а не считаться нами), `amount_usd` стоит брать из её
ответа/вебхука, если он даёт более точное число, чем наша оценка по курсу ЦБ.

## Критичные предложения (не обязательно, но сильно влияет на точность P&L)

1. **Два `Income` вместо одного.** Виджет `IncomeExpenseProfitChartWidget` уже показывает
   «Доход от выпуска карт» и «Доход от пополнений» двумя отдельными линиями графика
   (по `IncomeType::CardIssue` / `::CardTopup`) — это единственный способ отличить их в
   отчётах. Один общий `Income` на всю сумму заказа сделает так, что вся выручка «упадёт» в
   один тип, а по второму будет 0 — график перестанет показывать реальную структуру дохода.
   (`ProfitStatsWidget` сегодня считает прибыль одним общим числом без разбивки по типу — там
   эта проблема не проявится, но заводить привычку сливать типы в один `Income` всё равно не
   стоит: как только появится разбивка по типам ещё где-то, придётся её чинить задним числом.)

2. **Автоматический `Expense` на себестоимость выпуска.** Сегодня `Expense::create()`
   вызывается только вручную (из «Возвратов»). Если выпуск карты создаёт `Income`, но никогда
   не создаёт соответствующий `Expense`, то «Валовая прибыль» будет показывать 100% выручки без
   единой копейки себестоимости — то есть завышенную в разы прибыль. Без шага 5 (авто-`Expense`)
   на вопрос «будет ли P&L верным» ответ — однозначно нет.

3. **Себестоимость пополнения не отслеживается вообще.** В схеме есть `provider_issue_cost_usd`
   (стоимость выпуска), но нет аналогичного поля для стоимости самого пополнения — на
   `card_providers` такое поле было (`topup_fee_percent`) и его убрали при переносе экономики
   с провайдера на продукт, но на `CardProduct` замены не завели. Если CardsPro берёт с нас
   комиссию за пополнение (сверх суммы, которая ложится на баланс) — это сейчас нигде не
   считается и не видно в отчётах. Стоит явно проверить в документации/у CardsPro: пополнение
   идёт доллар-в-доллар, или есть комиссия. Если есть — нужно поле на `CardProduct`
   (например, `provider_topup_fee_percent`) и авто-`Expense` по нему аналогично шагу 5.

4. **Что делать, если оплата прошла, а CardsPro отклонил выпуск (`DECLINED`)?** Деньги с
   клиента уже списаны (`Income.payment_status = Paid`), а карты никогда не будет — ни в
   мгновенном ответе `issueCard()`, ни позже через вебхук/поллинг. Сейчас в этом месте
   алгоритм просто останавливается. Нужен явный процесс: либо автоматический возврат
   (в схеме уже есть модель `Refund`, но она сегодня не связана с этим сценарием), либо хотя бы
   алерт админу с явной пометкой «оплачено, но не выпущено» — иначе такие деньги будет видно
   только если специально искать `Income` без привязанной `Card`.

5. **Риск задвоения баланса при начальном пополнении.** Не подтверждено документацией:
   присылает ли CardsPro **ещё и** отдельный вебхук `CARD_TOPUP` на ту сумму, что была передана
   в `issueCard()` как стартовый баланс. Если да — баланс карты задвоится: один раз он
   выставится из `fetchCardSnapshot()` в `applyIssue()`, второй раз добавится через
   `CardsProWebhookHandler::handleTopup()`. Нужно проверить на песочнице до продакшена (в коде
   уже есть похожая пометка ⚠️ про недокументированность поля `san` в статусе операции — это
   из той же категории «проверить на реальном ответе»).

6. **Нет защиты от повторного оформления одного и того же заказа** (двойной клик, повтор
   запроса с фронта). Стоит добавить idempotency-key на API-метод оформления заказа — иначе
   при сетевом ретрае получится два независимых заказа с двумя независимыми списаниями.

7. **(Необязательно, не про P&L) Более гранулярный статус карты.** Сейчас `CardStatus::Pending`
   покрывает сразу три разных по смыслу состояния: «оформлено, ждём оплату», «оплачено, ждём
   CardsPro», «CardsPro в процессе». Для ЛК клиента и для отладки зависших заказов было бы
   удобнее их различать — но это расширение enum'а и не обязательно для корректности денег.
